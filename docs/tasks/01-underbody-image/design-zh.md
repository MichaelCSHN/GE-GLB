# 任务一：车底完整正下视图像

## 1. 目标与边界

任务一的原子产品是一张完整正下视图像。它由两个相互解耦的子系统构成：

1. 采集：从 Blender、Google Earth Pro 或未来实车获得同步的前后左右图像序列。
2. 拼接：只读取标准数据集，完成当前帧环视投影和时序车底补全。

任何来源适配器都不得把自身 API、坐标习惯或文件命名泄漏到拼接核心。隐藏正下视相机只能用于评测，不能成为重建输入。

## 2. 公共数据契约

数据集版本为 `ge-glb.dataset/v1`，必需文件如下：

| 文件 | 内容 |
| --- | --- |
| `manifest.json` | 来源、状态、坐标系、数量和工件索引 |
| `rig.json` | 巴士尺寸、相机模型、分辨率、内外参 |
| `trajectory.jsonl` | 路程、经纬度、局部 ENU 位姿和 `vehicle_to_world` |
| `frames.jsonl` | 帧号、相机、图像相对路径和相机世界位姿 |
| `fusion-plan.json` | `t_i`、历史帧、首帧延迟及候选优先级 |

固定坐标约定：

- 世界：以路径首点为原点的 ENU，单位米。
- 车体：`x` 向前、`y` 向左、`z` 向上。
- 相机：`x` 向右、`y` 向下、`z` 向前。
- KML heading：从北顺时针。
- tilt：0° 正下视，90° 水平。

图像路径必须相对数据集根目录，禁止绝对路径和 `..`。帧的唯一键为 `(frame_index, camera_id)`。

## 3. 模块划分

```text
src/geglb/
├─ core/                         坐标、相机、路径、Dataset、验证
├─ capture/
│  ├─ virtual/blender/           Blender平台能力
│  ├─ virtual/ge3d/              KML与GE 3D平台能力
│  └─ real/                      实采接口占位
├─ tasks/underbody_image/
│  ├─ capture_plan.py            任务一采集模型
│  ├─ temporal_selection.py      ti与历史候选
│  ├─ stitch_plan.py             来源无关拼接任务
│  ├─ compositor.py              平地IPM基线
│  └─ workflows/                 任务一与各后端组合
├─ products/                     三类最终产品协议
└─ workflows/comparison.py       MVP3跨来源配对
```

`CaptureBackend` 负责产生标准数据集；`StitchBackend` 只接收标准数据集。实采阶段需要实现时间同步、标定转换和图像导入，但不得修改数据集或拼接接口。

## 4. 时序拼接策略

目标帧 `t_i (i>0)` 的候选输入为：

- `t_i`：前、后、左、右全部相机。
- `t_i-1`：前、后、左、右全部相机。

上一帧前视具有较高软先验，侧视次之，后视较低但仍保留。最终选择必须按地面单元进行，依次考虑车体遮挡、视锥可见性、投影分辨率、入射角、图像质量和软先验，不能仅按相机名称硬切图像。

`t_0` 没有历史，等待 `t_1` 后利用全部未来相机回填，其中后视具有较高启动先验。若以后把 `history_frames` 调大，接口和数据格式保持不变。

## 5. MVP1：Blender

### 目的

尽快打通确定性的“场景—路径—相机组—图像序列—拼接—真值评测”闭环。

### 工作流

| 步骤 | 手工/程序 |
| --- | --- |
| 选择或整理 GLB 场景，确认单位为米 | 手工 |
| 将 GLB 原点与路径首点对齐，X东/Y北/Z上 | 手工 |
| 配置巴士尺寸、相机组、FOV和采样间隔 | 手工 |
| 解析 KML 路线并等距采样 | 程序 |
| 生成标准数据集和 `blender-job.json` | 程序 |
| Blender 后台导入 GLB、设置相机并逐帧 PNG 成像 | 程序 |
| 检查缺帧、尺寸和标定一致性 | 程序 |
| 生成来源无关的拼接任务 | 程序 |
| 检查场景材质、光照和路径穿模 | 手工确认 |

### 已完成

- `geglb blender plan`。
- 独立的 Blender 后台渲染脚本。
- 四环视相机与可选正下视真值相机。
- 标准数据集、采集报告路径及验证器。
- 无 Blender 环境也可测试的任务生成和脚本语法检查。
- 来源无关的平地 IPM 与加权融合基线，可直接输出带覆盖 alpha 的 BEV 序列。

### 待实机验证/后续开发

- 在目标 Windows Blender 版本上用真实城市 GLB 完成首轮渲染。
- 校验 GLB 尺度、原点、材质、灯光和相机 roll 符号。
- 增加深度、语义分割、车体遮挡 mask 和无车正下视真值。
- 在已有平地投影基线上增加曝光补偿、显式遮挡和评价指标。

### 验收条件

- 同一配置重复运行得到相同帧数、位姿和命名。
- 四相机在每个路线采样点均有一幅图像且无缺帧。
- 真值相机不出现在任何拼接输入中。
- 完成至少一段直线和一段弯道的透明车底重建。

## 6. MVP2：Google Earth Pro

### 目的

在真实地理三维影像上验证相同相机布局和拼接算法，同时接受 Earth Pro 的 GUI 与影像加载约束。

### 工作流

| 步骤 | 手工/程序 |
| --- | --- |
| 选择 Available 3D Area 和路线 | 手工 |
| 用“添加路径”绘制并确认 `ROUTE` | 手工 |
| 关闭干扰图层、阳光，确认地形和影像质量 | 手工 |
| 生成标准数据集、Camera Tour 和图像命名清单 | 程序 |
| 打开 KML、预热影像缓存 | 手工/后续自动化 |
| 逐视图 Save Image、恢复 Tour | 后续 Windows 自动化 |
| 验证图像并生成同一拼接任务 | 程序 |
| 检查署名、LOD跳变和缺帧 | 手工确认+程序 |

### 已完成

- `geglb ge-pro plan` 和兼容命令 `geglb plan`。
- KML `Camera`/`gx:Tour`、等待与逐视图暂停。
- 与 Blender 完全相同的 `manifest/rig/trajectory/frames/fusion` 数据接口。

### 待实机验证/后续开发

- Windows Earth Pro Save Image 控制器。
- UI 缩放、窗口尺寸、署名区域和文件对话框适配。
- 缓存预热、LOD 稳定检测、超时重试和漏帧恢复。
- 近地相机在不同 3D 城市中的可用高度/FOV边界验证。

### 验收条件

- 按 `frames.jsonl` 完成整段路线，无漏帧或可自动恢复。
- 相同路线重复采集的视点误差在设定阈值内。
- 输出通过标准验证器，拼接模块无需 GE 专用分支。

## 7. MVP3：Blender + GE Pro

### 目的

用同一相机、同一路线距离和同一拼接器比较可控仿真域与地理影像域，识别域差异而不是把两种图像直接混成一幅图。

### 已完成

- `geglb combine`。
- 按 `camera_id + nearest route distance` 配对。
- 距离容差、未配对统计和真值排除。

### 后续开发

- 每对图像的清晰度、颜色、纹理与投影覆盖比较。
- Blender 真值指标与 GE 无真值稳定性指标分开报告。
- 相机参数搜索同时在两个来源上运行，输出 Pareto 结果。
- 必要时加入特征级域适配，但不改变原始数据集。

### 验收条件

- 两个数据集均独立通过验证。
- 配对率、距离误差和相机覆盖有明确报告。
- 同一拼接器可分别运行于两个来源，不含来源条件分支。

## 8. 开发顺序

1. MVP1 实机冒烟：真实 GLB、短直线、四相机、10–20 个采样点。
2. MVP1 拼接基线实机验证：检查现有平地 IPM、当前帧融合和 `t_i-1` 车底补全。
3. MVP1 真值与优化：正下视评价、相机数/FOV/间隔参数搜索。
4. MVP2 控制器：缓存预热、Save Image、恢复、重试和日志。
5. MVP2 同构拼接：只替换数据集输入，不修改算法。
6. MVP3 联合评测：配对、域差异、统一参数选择。
7. 实采接口实现：时间同步、标定、里程计/定位和数据导入。

## 9. 当前环境能做与不能做的事项

当前代码环境可以完成协议、规划、脚本生成、静态检查、单元测试、模拟数据集和跨来源配对。真实 GLB 渲染需要安装 Blender 并获得场景文件；Earth Pro 采图需要 Windows GUI；真实道路采集需要相机、同步硬件和标定数据。这些是实机验证边界，不影响其余模块继续开发。
